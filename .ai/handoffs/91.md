# Issue

#91 [Bug] Audit log: concurrent sequence ordering race & fragile recovery

## Goal

Fix concurrency and recovery bugs in `core/src/audit.rs`: sequence ordering race in both sinks, sequence loss on write failure, fragile line-counting recovery, and TOCTOU between read and append in `JsonlAuditSink`.

## Current Plan

- Review requirements and acceptance criteria
- Implement solution in worktree
- Run verification suite

## Completed

- `InMemoryAuditSink::record`: moved sequence assignment inside the `events` mutex critical section, so physical push order always matches assigned sequence order.
- `JsonlAuditSink`: replaced separate `AtomicU64` sequence + `Mutex<File>` writer with a single `Mutex<JsonlSinkState { file, sequence }>` so sequence assignment and the write happen atomically under one lock.
- `JsonlAuditSink::record`: sequence is only advanced (`state.sequence = next`) after `write_all`/`flush` succeed, so a failed write no longer permanently loses a sequence number.
- `JsonlAuditSink::open`: opens the file once in `read(true).append(true)` mode and reuses that handle for both recovery and later appends (removes read-then-reopen TOCTOU window).
- Recovery now parses each line as `AuditEvent` via serde_json and takes the max observed `sequence`, instead of counting non-empty lines; non-UTF-8 bytes are handled via `String::from_utf8_lossy` and unparseable lines are skipped rather than corrupting the count.
- Added regression tests: concurrent in-memory ordering, concurrent JSONL sequence uniqueness, and recovery from corrupt/non-UTF-8 lines in the audit log.
- `cargo fmt --all -- --check` passes.

## Decisions

- Combined the JSONL sink's file handle and sequence counter into one `Mutex<JsonlSinkState>` (rather than keeping a separate atomic sequence) because the fix requires sequence assignment, the write, and the sequence commit to all happen under the same lock to close the TOCTOU/race/loss-on-failure issues simultaneously.
- Corrupt/non-UTF-8 lines are silently skipped during recovery (not treated as errors) per the issue's specified fix: derive starting sequence from max observed valid `AuditEvent.sequence`.
